# Cross-container shell access (clouve-ops)

You have an interactive shell into both side containers — `gibbon` and
`gibbon-mysql` — via SSH, using the `clouve-ops` operator account
pre-created in both images.

## Identity

| | |
|---|---|
| **User** | `clouve-ops` |
| **Sudo** | full passwordless `sudo` (effectively root) |
| **Auth** | per-pod ed25519 public key only — no password fallback |
| **Identity key** | `~/.ssh/clouve-ops` (mode 0600, owned by you) |
| **Source of key** | generated by gibbon-ai-studio's entrypoint on first boot, in `/clouve/ops-keys/id_ed25519` |
| **Lifetime** | one keypair per pod; wiped on `--cleanup` redeploy |

The key is materialised into `~/.ssh/clouve-ops` automatically by
`/etc/profile.d/clv-gibbon-skill.sh` on the first interactive login of
each shell session — you should never need to copy it yourself.

## Connecting

```bash
# Interactive shell, gibbon container (Apache + PHP)
ssh -i ~/.ssh/clouve-ops clouve-ops@${GIBBON_HOST}

# Interactive shell, gibbon-mysql container (Oracle Linux 9, MySQL 8)
ssh -i ~/.ssh/clouve-ops clouve-ops@${GIBBON_DB_HOST}

# Run a one-shot command (preferred for scripted operations)
ssh -i ~/.ssh/clouve-ops clouve-ops@${GIBBON_HOST} \
    "sudo tail -50 /var/log/apache2/error.log"
```

The first ssh to each host prints a host-key fingerprint warning;
either accept it interactively, or pass
`-o StrictHostKeyChecking=accept-new` on the first run. Subsequent
connections are silent — the host key is captured to
`~/.ssh/known_hosts`.

## When to use SSH vs. the TCP channels

| Operation | Use |
|---|---|
| Run a SQL query, count rows, read `gibbonSetting` | **TCP `mysql`** from the AI Studio container — faster, no SSH hop |
| `mysqldump` for backup | **TCP `mysqldump --host=${GIBBON_DB_HOST}`** — works fine over the wire |
| Read a Gibbon page or hit an API | **TCP `curl http://${GIBBON_HOST}/...`** |
| Tail `/var/log/apache2/error.log` | **SSH into gibbon**, then `sudo tail -f` |
| Run `php /var/www/html/cli/foo.php` (Gibbon CLI scripts) | **SSH into gibbon**, then `sudo php …` |
| `sudo apachectl reload` | **SSH into gibbon** |
| Inspect or edit `/etc/mysql/conf.d/*.cnf` | **SSH into gibbon-mysql**, then `sudo nano` |
| Restart `mysqld` (rare; usually pod restart is the right move) | **SSH into gibbon-mysql**, then `sudo systemctl restart mysqld` (if systemd present) or signal the process |
| Inspect filesystem under `/var/www/html` | **SSH into gibbon** — there is no shared filesystem mount |

## Safety gates apply across SSH

The same safety rules in this skill's `SKILL.md` and in the agent's
`~/.claude/CLAUDE.md` apply just as strictly when you're running
commands over SSH as when you're running locally. Specifically:

- **No destructive actions inside the target containers** (`apachectl
  stop`, `mysqld kill`, `DROP`, `TRUNCATE`, `rm -rf`) without an
  explicit user ack.
- **Edit `config.php` over SSH only after a diff + ack**; otherwise
  prefer the env-driven sync path that runs at container restart.
- **Never echo, copy, or transmit `~/.ssh/clouve-ops` itself** — same
  rule as for `~/.claude_api_key`.
- **Always `sudo` explicitly** for privileged commands rather than
  starting a root shell — keeps the audit trail in `/var/log/sudo.log`
  (where present) cleaner.

## Failure modes

| Symptom | Likely cause |
|---|---|
| `Permission denied (publickey)` | Identity key didn't get materialised yet — re-source `/etc/profile.d/clv-gibbon-skill.sh` or open a new shell |
| `Host key verification failed` | First connection — pass `-o StrictHostKeyChecking=accept-new` |
| `Connection refused` immediately after pod start | The target container's sshd hasn't started yet (it waits for the public key to appear, then for the daemon to bind) — retry after a few seconds |
| `Connection timed out` | Pod-internal DNS hasn't caught up, or the target container crashed — check `${GIBBON_HOST}` resolves and HTTP/MySQL still works |
| sshd never came up | Public-key file didn't appear — check that the `clouve_ops_keys` volume is mounted in all three containers and that gibbon-ai-studio's entrypoint ran cleanly |
